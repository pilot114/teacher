# backend

Хранилище прогресса для `topics`: вход по логину и паролю, результаты тестов лежат в SQLite.
Один бинарник без внешних зависимостей — фронт остаётся статикой и ходит сюда по HTTP.

## Запуск

```sh
go build -o teacher-api .
./teacher-api user add masha "Маша"   # спросит пароль
./teacher-api
```

По умолчанию слушает `:8090` и кладёт базу в `teacher.db` рядом с собой.

В Docker:

```sh
docker build -t teacher-api .
docker run -d -p 8090:8090 -v teacher-data:/data \
    -e ALLOW_ORIGIN=https://pilot114.github.io \
    -e JWT_SECRET=$(openssl rand -hex 32) \
    --name teacher-api teacher-api
docker exec -it teacher-api teacher-api user add masha "Маша"
```

## Настройки

| Переменная     | По умолчанию                            | Зачем                                                       |
|----------------|-----------------------------------------|-------------------------------------------------------------|
| `PORT`         | `8090`                                  | порт                                                         |
| `DB_PATH`      | `teacher.db`                            | файл базы                                                    |
| `ALLOW_ORIGIN` | `localhost,https://pilot114.github.io`  | откуда пускаем фронт; `localhost` — любой локальный порт     |
| `JWT_SECRET`   | берётся из базы                         | ключ подписи токенов                                         |
| `SESSION_DAYS` | `30`                                    | сколько живёт вход                                           |
| `CLAUDE_BIN`   | `claude`                                | Claude Code для арбитра ответов (см. ниже)                   |
| `JUDGE_MODEL`  | `haiku`                                 | модель арбитра                                               |
| `JUDGE_TIMEOUT_SEC` | `60`                               | сколько ждать решения арбитра                                |
| `JUDGE_THINKING_TOKENS` | `0`                            | бюджет арбитра на размышления; с ним в разы медленнее и на банке тестов не точнее |

`JWT_SECRET` можно не задавать: при первом запуске ключ генерируется и сохраняется в базе,
так что вход переживает перезапуск. Задайте его явно, если сервисов несколько.

## Учётки

```sh
./teacher-api user list
./teacher-api user add <логин> [имя]
./teacher-api user password <логин>
./teacher-api user delete <логин>       # вместе с прогрессом
```

Пароль спрашивается в консоли (без звёздочек) или берётся из переменной `PASSWORD`.
Хранится как PBKDF2-SHA256, 600 000 итераций.

## API

Все запросы, кроме входа, требуют заголовок `Authorization: Bearer <токен>`.

| Метод                        | Что делает                                                         |
|------------------------------|--------------------------------------------------------------------|
| `POST /api/login`            | `{login, password}` → `{token, expiresAt, user}`                    |
| `GET /api/me`                | кто вошёл                                                           |
| `GET /api/progress`          | все записи ученика: `{"класс/предмет\|тема": {attempts, best, total, passed}}` |
| `GET /api/tests`             | `?grade=seven` → оглавление тестов класса `{tests: {ключ: {title, titleRu, count}}}` |
| `GET /api/tests/item`        | `?key=<ключ темы>` → `{test, record}`; вопросы с ответами в `test` — только если тест закрыт |
| `POST /api/tests/start`      | `{key}` — начать попытку: она сразу засчитывается → `{number, questions, record}`, вопросы без ответов |
| `POST /api/tests/attempt`    | `{key, number, answers, violation}` — сдать попытку → `{record, attempt}` с учётом арбитра |
| `GET /api/history`           | лента от новых к старым: `?before=<id>&limit=50&type=theory,practice,test,attempt` → `{items, more}` |
| `POST /api/history/event`    | `{type, target}` — отметка: `theory` и `test` (открыл) с ключом темы, `practice` (нажал «Начать») с названием раздела |
| `GET /api/history/attempts`  | `?key=<ключ темы>` → все попытки теста со снимками вопросов и ответов |
| `GET /api/health`            | проверка живости                                                    |

### Тесты

Банк — `tests/<класс>.json` (`{"класс/предмет": {"тема": {title, titleRu, questions}}}`), вшит в бинарник
через `go:embed` и проверяется при старте: битый эталон не даст серверу подняться. После правки банка
сервер нужно пересобрать. Типы вопросов: `choice` (answer — номер варианта), `multi` (список номеров),
`number` (число, `tolerance` — допуск), `input` (строка или список допустимых написаний, `judge` — см. арбитра).

Фронт правильных ответов не видит, а итог теста пишет только сервер:

- вопросы отдаются только при `start`, и попытка засчитывается в этот же момент;
- начатая и не сданная попытка (закрыли вкладку, открыли тест заново) при следующем `item` или `start`
  закрывается как сорванная с нулём верных;
- эталон, пояснение и причина отказа арбитра уходят фронту (в тесте и в `history/attempts`), только когда
  тест закрыт: сдан или попытки кончились (`maxAttempts` в `bank.go`, на фронте — `MAX_ATTEMPTS`);
- повторная отправка той же попытки возвращает записанное.

### История

Лента (`events`) хранит, что ученик открывал, и сданные попытки; время ставит сервер.
Попытка (`attempts`) пишется в той же транзакции, что и результат теста: `{number, score, total, pass,
passed, violation, seconds, questions}`, где `questions` — снимок вопросов с эталоном и ответами ученика.
Он хранится целиком, чтобы разбор не зависел от последующих правок банка тестов; длительность считает сервер.
Номер попытки по теме уникален, поэтому повторная отправка того же результата ничего не дублирует.
При удалении учётки её история удаляется вместе с прогрессом.

### Арбитр ответов

Ответ со свободным вводом сервер сначала сверяет с эталоном. Если не совпало, а вопрос допускает разные
формулировки (в снимке у него `judge: true`), сервер перед сохранением попытки спрашивает
`claude -p --model haiku`, верен ли ответ по существу, и пересчитывает балл, зачёт и лучший результат.
Все такие ответы попытки уходят одним вызовом, обычно это 3–7 секунд. Решение с короткой причиной
сохраняется в снимке вопроса (`verdict: {correct, reason}`), и фронт показывает его в тесте и в истории.

- CLI запускается без инструментов, настроек и MCP, промпт идёт через stdin; ответ ученика — только данные.
- Одновременно работают не больше двух вызовов. Если CLI не найден, упал или не уложился в
  `JUDGE_TIMEOUT_SEC`, попытка сохраняется с проверкой по эталону, а причина пишется в лог.
- Повторная отправка уже сохранённой попытки возвращает записанное, и арбитр второй раз не вызывается.
- Решения не кешируются: на пограничных ответах модель непостоянна, а кеш закрепил бы первую ошибку.
- Сорванные попытки арбитру не отдаются: их ответы не проверяются.

CLI должен быть в `PATH` процесса и авторизован под тем же пользователем. При старте в лог пишется,
найден ли он.

После десяти неудачных попыток входа адрес блокируется на 15 минут.

## Что нужно фронту

Адрес API задаётся при сборке переменной `VITE_API_URL` (см. `topics/README.md`).
Страница на GitHub Pages отдаётся по HTTPS, поэтому API тоже должен быть за HTTPS —
иначе браузер не выпустит запросы. На проде ставьте его за nginx/Caddy с сертификатом.
